# 性能

## 后台语音加载对照（2026-10-11）

语音现已移出拼音启动关键路径。基线为 `6642e3c` 的独立 worktree，修改版来自
当前工作区；两者都以 release + `fastrace/enable` 构建，交替运行旧/新各 8 轮，
每轮新进程，语音及标点均开启、4 线程，词库/模型/用户词库副本一致。

| 指标 | 旧版中位数（最小～最大） | 新版中位数（最小～最大） |
|---|---:|---:|
| 拼音服务就绪 `daemon_startup` | 952.17ms（892.18～1036.35） | **5.27ms（4.87～7.01）** |
| 识别模型初始化 | 775.84ms（725.66～861.70） | 773.17ms（741.52～840.64） |
| 标点模型初始化 | 160.46ms（147.51～166.34） | 160.73ms（149.94～179.88） |
| 从启动 root 起点到语音可用 | 952.17ms（892.18～1036.35） | 956.97ms（903.80～1010.25） |

拼音服务就绪中位数减少约 **99.45%（约 181 倍）**；语音本身的初始化时间基本不变。
新版的语音可用时间按两个 root 的时间戳计算，包含后台调度和结果发布；旧版用
`daemon_startup` 结束作为语音服务也可用的时点。它们不包含进程创建、日志/Tokio
初始化或桌面 UI 完成切换。不能把该比值理解为每次按键快了 181 倍。

机器：Intel Core Ultra 5 336H，接电，governor `powersave`、EPP `performance`，
本组逐轮 1 分钟负载 2.47～3.10，未清理 OS 文件缓存。使用本次交替数据对照，
不拿前一组 851ms 的旧版绝对值判断回退；后台加载时 CPU 竞争仍可能影响实际输入延迟。

经用户授权完成实际 IBus 输入上下文验证，使用用户词库副本：

- 在 `voice_startup` 完成前创建输入上下文，输入 `nihao`，收到含“你好”的候选
  以及 `CommitText("你好")`，证明拼音不等待后台模型。
- 加载期间按住语音热键，就绪后模拟重复按下及释放，没有启动录音；重新按下才开始。
- **同一输入上下文**无需重新切换引擎，模型就绪后通过虚拟音频设备输入现有
  `data/asr/test_wavs/zh.wav`，收到 `CommitText("开放时间，早上九点至下午五点。")`。
- 第一次测试的 ALSA/Pulse 环境覆盖未生效，录音流仍指向默认设备，其结果不作为
  成功证据。最终测试用 PipeWire 的 `PIPEWIRE_NODE` / `PIPEWIRE_ALSA` 指定临时
  null sink monitor，并在播放前检查录音流的 source id 确实对应虚拟设备。
- 故意指定缺失的模型目录，语音提示不可用，拼音仍能候选并上屏“你好”。
- 模型仍在加载时 SIGINT，任务完成后结果被丢弃、退出码为 0，没有遗留加载进程。

Clippy（trace 开启）和 9 项引擎单元测试通过；新增测试覆盖加载中按住到就绪、
就绪前释放、失败结果对已有上下文可见。原始 trace、逐轮机器状态、测试脚本、
JSON 汇总和临时新旧二进制存于本机 `/tmp/cnt-background-voice-20261011/`，不入库。
验证结束后无 cnt 进程、无组件名称持有者，活动引擎为 `xkb:us::eng`，临时音频模块
已卸载。未修改已安装的二进制、模型、用户词库、IBus XML 或系统默认音频设备。

## 启动阶段（2026-10-11）

以下是实施后台加载前的首次测量。结论：**应将语音初始化移到后台，拼音先就绪**。
在当时机器状态下，语音为启动
关键路径增加约 846ms；语音重排器和 `load_voice` 合计占启动 root 的中位比例 99.4%。
这说明语音阻塞拼音就绪，但不能用这些数字解释此前缺少 D-Bus 名称握手造成的
首次激活超时（两者是不同问题，见 [启动协议](architecture.md#启动与首次激活)）。

测量版本 `6642e3c`，同一个 release 二进制，**开启 `fastrace/enable`**，
开启/关闭语音交替各 8 轮；每轮启动新进程，使用相同的已安装词库/LM/语音模型及
用户词库副本，语音配置为 4 线程、开启标点。所有 full 轮均出现 `voice ready`，
所有进程均以 SIGINT 优雅退出且退出码为 0。没有录音或发送按键。

| 阶段 | 中位数（ms） | 最小～最大（ms） |
|---|---:|---:|
| 词库、用户数据、LM 与解码器 | 3.99 | 3.94～4.13 |
| 语音重排器 | 2.11 | 1.96～2.35 |
| 语音初始化整体 | 844.38 | 836.95～862.09 |
| 其中：识别模型 | 686.38 | 683.61～708.12 |
| 其中：标点模型 | 150.07 | 146.40～152.26 |
| IBus 连接 | 0.46 | 0.39～0.68 |
| 导出 Factory | 0.006 | 0.005～0.008 |
| 申请组件名称 | 0.39 | 0.28～0.61 |
| **完整启动（开启语音）** | **851.53** | **844.22～868.97** |
| **完整启动（关闭语音）** | **5.16** | **4.96～5.49** |

父子 span 有包含关系，不可相加；各项中位数也不保证可加。
同一组 full/off 配对差值的中位数为 **846.29ms**。关闭语音只是对照配置，
不是后台加载实现，因此不能宣称异步化之后一定达到 5.16ms。

测量环境：Intel Core Ultra 5 336H，12 核，接电；governor `powersave`、EPP
`performance`；逐轮采样的 1 分钟负载为 1.94～2.33。保留系统文件缓存，未清理
全局 page cache；这是新进程初始化测试，**不是开机冷缓存或系统繁忙时的保证值**。
`daemon_startup` 从配置/资源初始化量到名称申请 IO 完成，不含进程创建、Tokio/
日志设施初始化，也不含 GNOME 完成切换、首次候选刷新，不能当成桌面端到端延迟。

原始逐轮日志、配置、机器状态及 JSON 汇总保存在本机
`/tmp/cnt-startup-diagnostic-20261011/`（临时诊断产物，不入库）。结束时确认：
无 `cnt-daemon` 进程，活动引擎为 `xkb:us::eng`，组件名称无持有者。
未安装或更新引擎/XML，未调用 `RegisterComponent`。

这一测量促成了上方的后台加载实现：基础拼音工厂先就绪，语音资源在线程中加载，
再发布给所有已有引擎；用同机、同 trace 的交替测量和实际链路验证检查结果。

## 关键设计（解码热路径）

都是先埋 span 看数据再改（见 AGENTS.md 的可观测性约定）：

- **词键缓存跨按键**：打字是增量的，敲 `womenzaigongzuo` 的每个字母都会把整个
  前缀重新解码，同一批词键（wo/women/zai/gongzuo…）反复查词库。缓存
  `词键 → 候选词表`（含 LM 下标、句首基础分、用户计数）
- **`learn()` 精确失效**：只丢这次动过的键，不整体清空 —— 否则每次上屏后的下一句
  都退回冷路径（实测每键 +26%）。真实打字的增量特性也在这里体现：追加一个字母只
  新增「以新末尾结束」的少数词键，前面位置的键全部命中，所以连续打字几乎全是热的
- **每个位置的词键只枚举一次**：词键只取决于「位置 + 音节格」，与假设无关；
  此前每条假设都重做字符串拼接与词库前缀查询，`BEAM=8` 就是 8 倍冗余
- **假设是 `Copy` 的小结构，路径存在 arena**：此前每条假设持有 `Vec<(Arc, Arc)>`，
  每次展开都要克隆整个 Vec（一次堆分配 + 全部引用计数），而每次解码有约 500 次展开
- **bigram 按「行」查**：同一前词的后继在 bigram 表里是连续区间。存活假设
  （≤ BEAM 条）先定位一次行，其所有后继在行内二分——把「几十次跨 60MB mmap 的
  随机二分」压成「一次定位 + 行内小范围二分」。注意行定位本身是两次全表二分，
  放到「每次展开」里会反而更慢（实测 +50%）
- **排序键先算好再排**：`ranked_words` 的比较器里曾调 `user_count`，每次比较都要
  抢用户库的锁 + 两次哈希查找，20 个候选就是上百次加锁
- **词库词零拷贝**：`ranked_words` 返回 `Cow`，词库词直接借 mmap，少一次 `String` 中转

## 历史记录（优化前对照）

本轮优化（词键缓存等上述设计）用「旧版/新版交替各跑 3 次」验证：
旧版 714~760µs、新版（热）~200µs —— 同一降频状态下的 **3.5x** 提升。

语音链路实测见 docs/voice-input.md（`bench`：平均 88~92ms，RTF 0.016；
`ctc_beam` 去掉多余 softmax 归一化后 20.1ms → 4.9ms）。
